DE-R01Arquitectura Databricks y elección de cómputoIngeniería de Datos · DE+
10 horas estimadasPrerrequisitos: AE08; SQL básicoPrimera prioridad
Objetivo

Dibujar la plataforma y justificar dónde ejecutar cada carga.

Notas de estudio

Una arquitectura separa almacenamiento persistente, cómputo y gobierno. Un notebook contiene código y resultados; no debe confundirse con el motor que lo ejecuta ni con la tabla que persiste sus datos. Un catálogo ayuda a organizar y controlar objetos; una tabla Delta incorpora metadatos transaccionales sobre archivos. Distinguir estas responsabilidades evita resolver un problema de permisos cambiando el tamaño del cómputo.

Antes de escoger recursos describe la carga: SQL o Python, interactiva o programada, volumen, latencia y requisitos de librerías. Después compara las opciones disponibles en tu workspace. Una recomendación del proveedor no equivale a una regla universal de costo: tiempo de arranque, duración, utilización y restricciones de la nube cambian el resultado. Registra supuestos y conserva evidencia de una ejecución pequeña.

Para tu transición desde analítica, la pregunta de estudio es cómo convertir una consulta que funciona en una carga repetible con recursos, permisos y responsable definidos. No necesitas memorizar todos los botones: debes explicar por qué una elección satisface el caso y qué limitación obligaría a cambiarla.

Ejercicio de razonamiento

Un dashboard SQL se consulta durante el día y un ETL Python corre cada noche. ¿Deben compartir exactamente el mismo cómputo?

Ver respuesta orientativa

No hay esa obligación. Evalúa un SQL warehouse para consultas y cómputo de Jobs compatible para el ETL; justifica aislamiento, disponibilidad, latencia y costo medido.

Práctica DE-R01

  1. Dibuja fuente → almacenamiento → cómputo → tablas → consumidor, marcando Unity Catalog.
  2. Clasifica seis cargas: BI, notebook exploratorio, ETL diario, streaming, librería especial y backfill.
  3. Para cada carga compara dos opciones de cómputo y una restricción.
  4. Ejecuta una consulta sintética pequeña y registra tipo de recurso, tiempo de arranque y ejecución.
  5. Redacta ADR-001 con elección, alternativa, supuestos y condición de revisión.
Criterio de aceptación

Entrega diagrama, matriz de seis casos y ADR. Debes explicar dónde viven los datos al apagar el cómputo y qué depende de tu workspace.

Lecturas dirigidas

  • Databricks · selección de cómputo ↗Documentación oficial; revisar disponibilidad por nube y workspace.
  • Databricks · Unity Catalog ↗Organización y gobierno de activos de datos.
  • Databricks · certificación Associate ↗Mapa de competencias de la certificación; no sustituye práctica de producción.
DE-R02Python para pipelines manteniblesBase compartida · DE+
10 horas estimadasPrerrequisitos: F07; Python básicoPrimera prioridad
Objetivo

Pasar de scripts de notebook a funciones con contratos, errores y pruebas.

Notas de estudio

Un pipeline combina lógica de transformación con efectos externos. Separa el cálculo puro de lectura, escritura y autenticación. Esta separación permite probar fechas inválidas o importes negativos sin conectarte a una plataforma. Los tipos y docstrings hacen explícito el contrato, pero no validan por sí solos las entradas de una API.

Representa importes con enteros en centavos o un tipo decimal apropiado, y define zona horaria antes de comparar timestamps. No conviertas silenciosamente valores desconocidos en cero: podrías alterar un saldo. Una excepción debe conservar contexto útil; los logs deben registrar lote y etapa sin exponer datos de personas.

Los reintentos sirven para fallos transitorios, no para corregir datos inválidos. Deben tener límite y una operación segura para repetir. En el laboratorio, una transacción de SQLite permite observar el vínculo entre escrituras y checkpoint. Ese mecanismo local enseña una propiedad importante, pero no demuestra tolerancia distribuida ni atomicidad entre servicios independientes.

Ejercicio de razonamiento

¿Por qué amount_cents=True debe rechazarse aunque isinstance(True,int) sea verdadero en Python?

Ver respuesta orientativa

El contrato requiere un importe entero, no un booleano. type(x) is int distingue este caso; una validación de dominio debe ser más precisa que una conversión implícita.

Práctica DE-R02

  1. Ejecuta python pipeline.py dentro de practicas-de.
  2. Lee validate y añade casos de campo ausente, booleano y fecha imposible.
  3. Implementa ejercicios/reconstruir.py antes de consultar ingest.
  4. Divide extracción, validación, transformación y publicación en funciones explicables.
  5. Ejecuta python -m unittest -v y documenta dos errores que detectaste.
Criterio de aceptación

Las 14 pruebas incluidas pasan; tu implementación adicional preserva las versiones más recientes y elimina eventos borrados. Explica cada función sin asistencia.

Lecturas dirigidas

  • Python · sqlite3 ↗Referencia para conexiones, parámetros y transacciones del laboratorio local.
  • Pro Git · libro abierto ↗Control de versiones, ramas y colaboración; traducción al español disponible.
DE-R03SQL, transacciones y planes de ejecuciónBase compartida · DE+
10 horas estimadasPrerrequisitos: AE01; F07Núcleo
Objetivo

Escribir consultas correctas, comprobar granularidad y comprender una transacción.

Notas de estudio

Una consulta debe comenzar por el significado de una fila. Un join entre dos relaciones uno-a-muchos puede multiplicar importes aunque su sintaxis sea correcta. Agrega cada lado al grano requerido o conserva una tabla de hechos separada. Las funciones de ventana permiten ordenar versiones sin perder el detalle, siempre que definas un desempate estable.

Una transacción agrupa cambios que deben confirmarse o revertirse juntos. Esto no elimina la necesidad de controlar concurrencia ni permite asumir que SQLite y PostgreSQL tienen idéntico aislamiento. Usa parámetros para valores en consultas: concatenar entradas convierte datos en código. Los nombres de objetos requieren validación o composición segura específica.

EXPLAIN permite investigar el plan elegido. Un índice puede mejorar filtros selectivos y penalizar escrituras; en almacenamiento columnar distribuido, particiones y organización de archivos cumplen otras funciones. Compara resultados además de tiempos: una consulta rápida que duplica filas no es una optimización válida.

Ejercicio de razonamiento

Una factura tiene tres líneas y dos pagos. ¿Cuántas filas produce unir ambas relaciones por factura?

Ver respuesta orientativa

Seis. Para sumar a nivel factura, agrega primero líneas y pagos por separado; no uses DISTINCT como parche sin justificar qué duplicados elimina.

Práctica DE-R03

  1. Consulta bronze, silver y quarantine del laboratorio.
  2. Escribe ROW_NUMBER para elegir versión y compara con la solución Python.
  3. Introduce un join multiplicativo y demuestra el error con cifras.
  4. En PostgreSQL de práctica compara EXPLAIN antes y después de un índice.
  5. Inyecta el fallo del laboratorio y verifica que no avanza el checkpoint.
Criterio de aceptación

Resultados SQL y Python coinciden; incluye prueba del join y explica rollback. Registra motor y versión al comparar rendimiento.

Lecturas dirigidas

  • PostgreSQL · tutorial ↗Joins, claves, transacciones y ventanas; continuar con SQL y EXPLAIN.
  • UC Berkeley · CS186 ↗Curso de bases de datos y exámenes públicos con soluciones; ampliación académica.
  • Python · sqlite3 ↗Referencia para conexiones, parámetros y transacciones del laboratorio local.
DE-R04Modelado dimensional, historia y métricasBase compartida · DE+
10 horas estimadasPrerrequisitos: AE02, AE03 y AE06Núcleo
Objetivo

Diseñar hechos y dimensiones sin perder historia ni significado de métricas.

Notas de estudio

Un hecho representa un evento o una observación al grano acordado. Un saldo diario y un desembolso no se suman de la misma manera a través del tiempo. El modelo debe expresar unidades, moneda, fecha de negocio y cobertura antes de construir indicadores. Una métrica requiere numerador, denominador, exclusiones y tratamiento de correcciones.

Una dimensión SCD tipo 2 conserva intervalos de vigencia de atributos. No es equivalente a guardar solo la última versión del evento. Un join temporal necesita una convención de intervalos, por ejemplo inicio inclusivo y fin exclusivo, y pruebas para evitar intervalos superpuestos. Para correcciones retroactivas puede ser necesario separar tiempo efectivo y tiempo de conocimiento.

En crédito, una política vigente al decidir puede diferir de la política actual. En salud, una clasificación puede cambiar después del alta. Conservar estas diferencias hace reproducible un análisis. Tu experiencia con KPIs y reglas de negocio es útil para documentar esas decisiones; la práctica consiste en implementarlas y probarlas.

Ejercicio de razonamiento

Un cliente cambia de segmento el 10 de enero. ¿Con qué segmento se clasifica una operación del 8 de enero?

Ver respuesta orientativa

Con el segmento vigente el día 8 si la métrica es histórica por vigencia. Usar el actual responde otra pregunta; debe declararse expresamente.

Práctica DE-R04

  1. Diseña fact_credit_event y dim_customer_scd2 con claves y grano.
  2. Crea dos versiones de segmento y un evento antes y después del cambio.
  3. Implementa join por [valid_from,valid_to).
  4. Añade prueba de no solapamiento y una sola fila actual.
  5. Documenta una métrica de aprobación y su denominador.
Criterio de aceptación

El join temporal devuelve exactamente una dimensión por hecho; entrega DDL, tres casos límite y diccionario de métricas.

Lecturas dirigidas

  • Kimball Group · técnicas dimensionales ↗Granularidad, hechos, dimensiones y tratamiento de historia.
  • PostgreSQL · tutorial ↗Joins, claves, transacciones y ventanas; continuar con SQL y EXPLAIN.
DE-R05Ingesta incremental, CDC y datos tardíosIngeniería de Datos · DE+
12 horas estimadasPrerrequisitos: DE-R02 y DE-R03; AE03Núcleo
Objetivo

Procesar lotes sin duplicar y distinguir orden de llegada de orden de versión.

Notas de estudio

Ingestar implica identificar qué se leyó, desde dónde y con qué contrato. Un checkpoint registra avance de procesamiento; no demuestra que el dato sea correcto. Un diseño recuperable conserva evidencia de entrada, identifica el lote y confirma su publicación de forma coherente. El cursor de extracción y la versión de una entidad resuelven problemas diferentes.

CDC representa cambios: inserciones, actualizaciones y borrados. Si llega tarde una actualización antigua, no debe reemplazar la versión vigente. Si eliminas físicamente todo rastro de un borrado, un evento anterior puede resucitar la entidad. Un tombstone conserva la versión del borrado para impedirlo. Tampoco basta elegir una fila al azar cuando dos payloads comparten clave y versión: eso es un conflicto del contrato.

Usar MAX(fecha_evento) como único cursor puede perder correcciones antiguas. Evalúa secuencias de origen, fecha de modificación, solapamiento controlado y reconciliación periódica. En el laboratorio el origen entrega lotes contiguos y una versión entera por entidad; son supuestos explícitos, no garantías universales de una API.

Ejercicio de razonamiento

Llega B versión 2 DELETE y después B versión 1 UPSERT. ¿Cuál debe ser el estado vigente?

Ver respuesta orientativa

B debe seguir borrado. Conserva versión 2 como tombstone y rechaza que una versión inferior cambie el estado.

Práctica DE-R05

  1. Ejecuta los tres lotes sintéticos y observa los cambios de A y B.
  2. Repite cada lote: silver y gold deben permanecer iguales.
  3. Inyecta un fallo a mitad del lote y comprueba rollback.
  4. Cambia el contenido de un lote ya confirmado y comprueba rechazo.
  5. Diseña paginación y cursor para una API simulada con un lote faltante.
Criterio de aceptación

A=12000, C=7000 y D=3000 centavos activos; B borrado. Total 22000. Reintentos, lote faltante y payload conflictivo tienen pruebas.

Lecturas dirigidas

  • Databricks · Auto Loader ↗Ingesta incremental de archivos; contrastar fuentes, esquema y checkpoints.
  • Apache Airflow · buenas prácticas ↗Tareas repetibles, particiones explícitas y recuperación.
  • Databricks · MERGE en Delta ↗Actualizaciones, inserciones y borrados; revisar duplicados y versión de runtime.
DE-R06Delta Lake y publicación Bronze–Silver–GoldIngeniería de Datos · DE+
12 horas estimadasPrerrequisitos: DE-R01, DE-R04 y DE-R05Núcleo
Objetivo

Trasladar el contrato local a tablas Delta y verificar publicación repetible.

Notas de estudio

Bronze, Silver y Gold describen responsabilidades, no una garantía automática de calidad. Bronze permite rastrear entradas; Silver resuelve tipos, claves y reglas; Gold ofrece productos al grano del consumidor. Conviene conservar información de origen y transformación para poder investigar diferencias entre capas.

Un MERGE requiere que la fuente esté preparada para identificar cambios inequívocos. Deduplicar por clave y versión es distinto de eliminar filas idénticas. Un orden no determinista puede producir resultados diferentes entre ejecuciones. Conserva el marcador de borrado y condiciona la actualización a una versión posterior cuando ese sea el contrato del origen.

La atomicidad de una tabla no convierte varias escrituras a distintas tablas en una transacción global. Por eso se necesita una estrategia de publicación y reconciliación antes de exponer resultados parciales. El notebook incluido tiene un caso sintético acotado: crea una fuente de práctica, actualiza estado y comprueba Gold. No implementa SCD2, ingesta de una API real ni coordinación distribuida completa.

Ejercicio de razonamiento

¿Por qué el ejemplo conserva op=DELETE en Silver pero lo excluye de Gold?

Ver respuesta orientativa

Silver necesita recordar la versión del borrado; Gold expone solo eventos activos. Borrar el tombstone permitiría reinsertar una versión antigua en futuros lotes.

Práctica DE-R06

  1. Configura catálogo y schema de práctica en databricks/pipeline_demo.py.
  2. Ejecuta prepare, transform y quality y conserva salida de reconciliación.
  3. Repite transform: no deben aumentar filas ni totales.
  4. Introduce una versión conflictiva y confirma fallo antes de publicar.
  5. Extiende con un lote tardío y documenta la estrategia de relectura.
Criterio de aceptación

Fixture Databricks: total 19000 centavos, A=12000 y C=7000. Este fixture no incluye D del laboratorio local. Conserva evidencia de dos ejecuciones iguales.

Lecturas dirigidas

  • Databricks · MERGE en Delta ↗Actualizaciones, inserciones y borrados; revisar duplicados y versión de runtime.
  • Databricks · Auto Loader ↗Ingesta incremental de archivos; contrastar fuentes, esquema y checkpoints.
  • Databricks · Unity Catalog ↗Organización y gobierno de activos de datos.
DE-R07PySpark y rendimiento con evidenciaIngeniería de Datos · DE+
12 horas estimadasPrerrequisitos: DE-R03 y DE-R06; AE07Núcleo
Objetivo

Entender planes, shuffles y particiones sin sustituir medición por intuición.

Notas de estudio

Spark construye un plan y ejecuta transformaciones cuando una acción necesita resultados. Una operación aparentemente pequeña puede mover datos entre ejecutores. Joins, agrupaciones y ordenamientos merecen atención porque pueden producir shuffles y concentrar trabajo en claves frecuentes. La cantidad de filas por sí sola no describe el costo: importan anchura, distribución y número de archivos.

Empieza por verificar esquema, filtros y columnas necesarias. Después inspecciona el plan y mide una ejecución base. Si una clave domina el volumen, algunas tareas pueden durar mucho más que las demás. Aumentar recursos sin examinar ese sesgo puede esconder el problema sin resolverlo. Un broadcast necesita una relación realmente pequeña y memoria suficiente.

Cada experimento debe comparar misma entrada y misma semántica. Cachear solo ayuda cuando se reutiliza una representación y su costo de memoria compensa. Evita collect sobre datasets grandes; el laboratorio usa collect únicamente para una salida Gold diminuta. No extrapoles el tiempo de seis filas a una carga empresarial.

Ejercicio de razonamiento

¿Un pipeline con más particiones será siempre más rápido?

Ver respuesta orientativa

No. Hay costos de planificación, tareas y archivos pequeños. Se compara el plan, distribución y tiempos con un tamaño de entrada representativo.

Práctica DE-R07

  1. Genera al menos 100000 filas sintéticas con una clave dominante.
  2. Registra plan, duración y distribución de tareas del baseline.
  3. Compara filtro temprano, proyección de columnas y estrategia de join.
  4. Verifica equivalencia de resultados con conteos y agregados por clave.
  5. Entrega un informe de una página con la intervención útil y la que no ayudó.
Criterio de aceptación

Informe reproducible con tres ejecuciones por alternativa, configuración y resultado equivalente. No declares una mejora si la variación supera el efecto.

Lecturas dirigidas

  • UC Berkeley · CS186 ↗Curso de bases de datos y exámenes públicos con soluciones; ampliación académica.
  • Apache Spark · Structured Streaming 3.5.8 ↗Referencia versionada para tiempo de evento, watermarks y estado; adaptar al runtime.
  • Databricks · selección de cómputo ↗Documentación oficial; revisar disponibilidad por nube y workspace.
DE-R08dbt: modelos, pruebas y semánticaBase compartida · DE+
12 horas estimadasPrerrequisitos: DE-R03, DE-R04 y DE-R05Núcleo
Objetivo

Construir un DAG analítico versionado y probar supuestos del dato.

Notas de estudio

dbt organiza transformaciones SQL y sus dependencias en un proyecto. Una referencia entre modelos expresa relación de construcción, pero no prueba que el join sea correcto ni que la métrica esté bien definida. Las pruebas deben cubrir claves y también reglas relevantes del negocio.

Distingue pruebas sobre resultados de pruebas unitarias de lógica con entradas controladas. Un modelo puede compilar y devolver datos erróneos. Las pruebas singulares devuelven filas que violan una condición; un resultado vacío representa cumplimiento del supuesto evaluado, no una validación total.

Un modelo incremental guarda estado y exige razonar sobre nuevas filas, correcciones y reconstrucción. Antes de hacerlo incremental, construye una versión completa correcta y compara ambas. La plantilla incluida usa vistas y un seed para facilitar un primer recorrido con PostgreSQL. Convertirla en incremental es un ejercicio posterior: configura unique_key, estrategia compatible y una política explícita de datos tardíos. No copies una estrategia de otro adaptador sin comprobar soporte.

Ejercicio de razonamiento

¿Configurar unique_key equivale a validar que la fuente tiene una sola versión vigente por clave?

Ver respuesta orientativa

No. La clave guía la materialización compatible, pero la fuente necesita pruebas y preparación. Conserva la prueba de conflictos y verifica unicidad del resultado.

Práctica DE-R08

  1. Crea PostgreSQL de práctica y un entorno aislado con adaptador dbt-postgres compatible.
  2. Configura variables de entorno siguiendo profiles.example.yml.
  3. Ejecuta dbt debug, dbt seed y dbt build.
  4. Añade un conflicto de versión al seed y comprueba que no_conflicting_versions falla.
  5. Implementa una alternativa incremental y compárala contra la reconstrucción completa.
Criterio de aceptación

Gold suma 19000 para el fixture dbt; pruebas de unicidad, contrato y conflictos pasan. Entrega manifest y run_results sin credenciales.

Lecturas dirigidas

  • dbt · modelos incrementales ↗Configuración incremental; revisar estrategia y adaptador instalados.
  • dbt · pruebas de datos ↗Pruebas genéricas y SQL singular; comprobar compatibilidad de versión.
  • PostgreSQL · tutorial ↗Joins, claves, transacciones y ventanas; continuar con SQL y EXPLAIN.
DE-R09Lakeflow Jobs: dependencias, reintentos y reparaciónIngeniería de Datos · DE+
12 horas estimadasPrerrequisitos: DE-R05 y DE-R06Primera prioridad
Objetivo

Operar un DAG que falla de forma diagnosticable y se recupera sin duplicar.

Notas de estudio

Un DAG describe qué tareas pueden comenzar después de otras. No garantiza por sí mismo que las escrituras de una tarea sean seguras para repetir. Cada tarea debe definir entrada, salida, rango temporal y estrategia de publicación. Usa parámetros explícitos para ejecutar un periodo pasado en lugar de depender de la fecha actual.

Un reintento automático conviene ante una interrupción transitoria; una violación de contrato necesita investigar o aislar el dato. Reparar una ejecución permite recuperar tareas fallidas y dependientes según su estado y configuración. La lógica debe tolerar que una tarea vuelva a comenzar después de haber escrito algo.

El ejemplo prepara, transforma y valida. Para demostrar dominio añade una publicación condicionada a calidad, un fallo controlado y un backfill por fecha. Observa qué tareas se ejecutan y cuáles quedan bloqueadas. No confundas Job exitoso con dato correcto: la última tarea necesita reconciliar el producto que consumirá el usuario.

Ejercicio de razonamiento

Transform escribió parte de la salida y falló. ¿Basta pulsar Repair para asegurar que no habrá duplicados?

Ver respuesta orientativa

No. Primero verifica idempotencia y estado parcial; la reparación vuelve a ejecutar tareas, pero no corrige automáticamente su semántica de escritura.

Práctica DE-R09

  1. Despliega el Job de tres tareas en un entorno de desarrollo compatible.
  2. Inyecta un fallo controlado y captura el grafo y su causa.
  3. Corrige, repara y compara con una ejecución limpia.
  4. Agrega un parámetro de fecha y reproduce un día anterior.

Objetivo

Definir éxito por frescura, corrección y recuperación, además del estado del Job.

Notas de estudio

DE-R14Streaming, tiempo de evento y límites de garantíasProfundización · DE+

Objetivo

Notas de estudio

Tiempo de evento y tiempo de procesamiento responden a preguntas diferentes. Un evento puede llegar después de otros más recientes y modificar una ventana histórica. Preguntas que debes poder contestar

  1. ¿Qué representa una fila y qué pasa al unir dos relaciones uno-a-muchos?
  2. ¿Qué diferencia hay entre versión del evento y secuencia del lote?
  3. ¿Qué ocurre si el proceso cae después de escribir y antes de confirmar avance?
  4. ¿Cómo procesas una corrección de hace dos meses y un borrado tardío?
  5. ¿Qué propiedad comprueba tu baseline que no comprueba el conteo de filas?
  6. ¿Por qué elegiste ese cómputo y qué dato te haría cambiarlo?
  7. ¿Cómo sabes que un Job exitoso produjo un producto utilizable?
  8. ¿Qué parte implementaste y qué parte sigue siendo plantilla o propuesta?

Protocolo de lectura académica

Por cada fuente conserva referencia y versión, tres conceptos, un supuesto, una limitación y una práctica que la contraste. Para un artículo formula pregunta, método, resultado y amenaza a la validez; replica un caso pequeño antes de generalizar.
